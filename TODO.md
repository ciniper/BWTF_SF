# B. Sewage alert system

**Goal:** A reliable, real-time **text-alert** system for combined-sewer-overflow (CSO / sewage dumping) events in San Francisco, built for the Surfrider SF Blue Water Task Force.

## Snapshot — where it stands today

- **Detection works.** `core/sfpuc_api.py` pulls live station status + CSO flags from SFPUC's internal LIMS API; `core/monitoring.py` adds SF Gov bacteria data + AB-411 logic; `core/weather_tides.py` adds rain/tide context.
- **Channels exist.** `core/notifiers.py` supports Twilio SMS, free email-to-SMS gateways, SMTP email, Slack, Discord, and console.
- **Subscriptions work per-site.** `core/subscriptions.py` + `data/subscriptions.json`, with targeted dispatch in `core/cso_alerts.py`.
- **Dashboard runs locally.** `dashboard.py` serves `localhost:8080` via Python's single-threaded stdlib server; HTML is generated inline (~1,695 lines).
- **Test harness exists.** Simulated CSO events (`SimulatedCSOStore`) let you fire fake events without waiting for a real one.

**Central gap:** detection and dispatch are **manual** — a real CSO only goes out when someone clicks the dashboard button or runs `run_subscription_alerts.py` by hand. Nothing polls SFPUC on a schedule, remembers what it already sent, or runs unattended. State is local JSON files, and there are no tests. Most items below build toward closing that loop.

Brevo's reply landed in `net._http_response`, which pg_net purges after ~6 hours (`pg_net.ttl`), so after that a failed send was indistinguishable from a good one, and a silent failure in a safety alert system is the worst case. The subject and body were rendered at send time and never stored either. Two levels:
  1. **Did Brevo accept it? — BUILT (015; `features/alerts/deliveries.py`; Deliveries panel on `/alerts`).** `alert_deliveries` = one row per message (recipient × channel) with the rendered subject / text / HTML / SMS text, the renderer's version, pg_net's request id, and Brevo's reply: `http_status` (201 = accepted), `message_id`, `error`. `bwtf_dispatch_live` inserts the row before each POST and tags the Brevo request `bwtf-delivery-<id>`, each in its own exception block — the POST itself is untouched and never swallowed, so a fault in the new code costs a log row, never an email. An after-insert trigger on `alert_log` links the rows to their event (the callers in 006/009/011 are not redefined). `bwtf_check_deliveries` — its own pg_cron job every minute, not the tick — reads the reply from `net._http_response` while it is still there, stamps status / messageId / error, logs failures to `watcher_errors` (kind `delivery`), and marks rows whose reply was purged unread. The Python manual dispatch writes complete rows itself (it sees the reply synchronously). Storage ≈ 3.4 KB per message. **Apply** in a dry spell with no simulation active, then run one simulated alert to the test recipients and check the rows show 201 + a message_id a minute later (DEPLOY.md § 015). Not built: pushing failures into the heartbeat — they are in `watcher_errors` and on the panel.
  2. **Did it reach the inbox? — BUILT (level 2, 2026-09-29; no migration).** Accepted ≠ delivered, so `deliveries.poll_brevo()` runs as a side job of the production forecast refresh (every 30 min, after the snapshot is stored — `features/forecast/page._poll_deliveries`, never raises): one paged call to Brevo's events API (`GET /v3/smtp/statistics/events`, last 8 days) for the accepted rows of the last 7 days that have no final state, matched on `messageId` (else the `bwtf-delivery-<id>` tag, which Brevo returns comma-joined), stamping `delivery_state` / `delivery_at`: delivered wins, else the latest hard failure (hard_bounce / blocked / spam / invalid / error, its reason into `error`), else soft_bounce, else deferred; soft_bounce and deferred are re-asked. Key: `BREVO_API_KEY` env, else `watcher_config.brevo_api_key`. Poll, not webhook (decided 2026-09-28): no public endpoint, nothing to spoof, a week of downtime loses nothing (Brevo keeps 90 days). The panel shows the states with reasons and lists **Not arriving** addresses (bounced / blocked / spam in the last 30 days) for Chase to review — nothing is deactivated automatically. Dry-run 2026-09-29 against the real API: the simulated test alert was delivered one second after Brevo accepted it. Left out: Brevo's aggregated daily counts on the panel; clicks. **Opens kept (016, Chase 2026-09-29):** `opened_at` = the first `opened` event, stamped by the same poll (pixel-based — null is not proof of unread; Apple's `loadedByProxy` ignored). Brevo tracks opens/clicks by default; turn tracking off in its transactional settings if the alerts should not track their readers, and the column stays null.

# C. Data comparison dashboard

**Goal:** Compare water-quality results for the same SF beaches between the two independent monitoring programs — the **Surfrider Blue Water Task Force** volunteer lab and **public city data** (SF Gov Open Data + SFPUC) — to build trust, surface divergence, and tell a public story about beach safety.

## Shipped (v1)
- `features/comparison/bwtf_api.py` — client for the public BWTF database (AWS AppSync GraphQL; SF chapter = **lab 76**). Pulls each site's latest Enterococcus result + CA thresholds, and exposes a historical series (`fetch_history`).
- `features/comparison/comparison.py` — pairs each BWTF site with its city counterpart (reusing `SFPUC_TO_SFGOV_SOURCES`), grades both against the CA single-sample max (104 MPN/100mL), and computes agreement, value delta, and sampling-day gap.
- `features/comparison/page.py` — `/compare` page + `/api/compare` + `/api/site-history`, served by the Flask app (`app/wsgi.py`) and linked from the landing page.
- Compares the **6** sites BWTF currently publishes for SF: Aquatic Park, Baker Beach at Lobos Creek, China Beach, Crissy Field East, Ocean Beach at Lincoln Way, Ocean Beach at Vicente St.
